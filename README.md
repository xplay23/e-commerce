# NORD: запуск на своём сервере

Магазин работает без Supabase. В текущем коде уже были Vue 3, PHP REST API и MySQL;
проект подготовлен для самостоятельного размещения через Docker Compose.

## Как это работает

```text
Локально: браузер → localhost:8080 → Nginx → PHP-FPM → MySQL
На VPS:  браузер → HTTPS / Caddy → Nginx → PHP-FPM → MySQL
```

- `web`: собирает Vue в Docker и отдаёт готовые файлы через Nginx. Запросы `/api/*`
  передаются в PHP. Прямые переходы на `/catalog`, `/account` и другие страницы работают.
- `backend`: PHP 8.5.12 с `pdo_mysql`. В нём работают регистрация, вход, каталог,
  избранное, заказы и управление товарами. Пароли пользователей хешируются;
  в MySQL хранятся хеши токенов авторизации.
- `db`: MySQL 8.4. Порт 3306 не публикуется. Отдельный пользователь приложения
  подключается к базе по имени `db` во внутренней сети Docker.
- `mysql_data`: постоянный Docker volume. Перезапуск, пересборка и обычный
  `docker compose down` сохраняют данные. `down -v` удаляет том и данные — не используйте
  эту команду для обычной остановки.
- `caddy`: дополнительный контейнер для VPS, который получает и обновляет TLS-сертификат.
- `migrate`: применяет миграции перед запуском PHP. Существующий том базы сохраняется.
- `mail-worker`: отправляет письма из зашифрованной очереди с повторными попытками.
- `mailpit`: только в `compose.local.yaml`; принимает тестовые письма, не отправляя их в интернет.

Секреты хранятся в локальном `.env.docker`, исключены из Git и контекста сборки.
В браузер попадает только адрес `/api`, паролей базы в JavaScript нет.

## Что требуется

- Локально на Windows: Docker Desktop с работающим Linux Engine и WSL 2, Node.js 22+
  для вспомогательных npm-команд.
- На VPS: Linux, Docker Engine и Docker Compose v2+, SSH-доступ. Node.js и PHP на самом
  сервере не обязательны: приложение собирается в контейнерах.
- Для публичного HTTPS: домен, DNS A/AAAA на адрес VPS, доступные порты 80 и 443.
  Начальная оценка ресурсов для небольшого магазина: 2 vCPU, 4 GB RAM, 25+ GB SSD;
  фактическая потребность зависит от нагрузки, сборки и объёма базы.

## Локальный запуск

Из корня проекта:

```bash
npm run docker:setup
npm run docker:up
```

Первая команда генерирует независимые случайные пароли приложения и root в `.env.docker`.
`docker:up` проверяет готовность Docker Engine; на Windows при необходимости запускает
Docker Desktop и ожидает Linux Engine. После запуска контейнеров проверяет `/api/health`.
Повторный запуск сохраняет существующие пароли и ключи и добавляет недостающие ключи шифрования.
Вторая команда использует `compose.yaml` и `compose.local.yaml`, собирает образы, создаёт базу,
применяет схему и ожидает готовности сервисов. Инициализация SQL выполняется только при
создании пустого тома MySQL. Демотовары и администратор автоматически не добавляются.

Сайт: <http://localhost:8080>. Проверка базы через API: <http://localhost:8080/api/health>.
Тестовая почта Mailpit: <http://localhost:8025>. Письма видны здесь, а не в реальном почтовом ящике.
По умолчанию HTTP доступен только на этом компьютере (`127.0.0.1`).
При занятом порте измените `HTTP_PORT` и `FRONTEND_URL` в `.env.docker`.

Добавить восемь демонстрационных товаров и пять категорий в пустой каталог:

```bash
docker compose --env-file .env.docker exec backend php bin/seed.php
```

Скрипт откажется работать при наличии товаров, чтобы не перезаписать реальный каталог.
Создать администратора, указав свой email и новый пароль (пароль вводится скрыто):

```bash
docker compose --env-file .env.docker exec backend php bin/create-admin.php admin@example.com
```

Готовой учётной записи с известным паролем нет. Вход: `/login`, управление товарами: `/admin`.
Команда создания администратора не меняет существующие учётные записи.

Проверка и управление:

```bash
npm run test:smoke
npm run test:security
npm run test:backup
docker compose --env-file .env.docker ps
npm run docker:logs
npm run docker:down
```

Smoke-проверка создаёт временные товары и пользователей, проверяет SPA, каталог,
CSRF, cookie-сессии, подтверждение email, блокировку после третьего неверного пароля,
сброс через SMTP/Mailpit, одноразовость и срок ссылок, отзыв сессий, заказы и права администратора.
После выполнения удаляет свои данные. Она разрешена только в локальной конфигурации
с `ALLOW_SMOKE_TESTS=1` и не запускается в production.

### Если Docker на Windows не запускается

На этом ПК отсутствовали WSL и компоненты Windows для Linux-контейнеров.
При настройке 4 ноября 2026 включены `VirtualMachinePlatform` и
`Microsoft-Windows-Subsystem-Linux`, установлен официальный WSL 3.0.3
(проверены SHA-256 и подпись Microsoft). Windows требует перезагрузку для применения изменений.
До неё Docker Linux Engine и API в контейнерах не запускаются.

Из корня проекта повторить настройку можно командой:

```powershell
npm run docker:windows-setup
```

Она запрашивает административные права через UAC, включает компоненты и устанавливает
подписанный WSL MSI из официального репозитория Microsoft. Компьютер автоматически не
перезагружается, данные Docker не удаляются. Состояние и журнал: `logs/docker-setup/status.json`
и `logs/docker-setup/setup.log` (исключены из Git и Docker-контекста).

Для ручной настройки можно использовать стандартную команду Microsoft.

Откройте PowerShell **от имени администратора**:

```powershell
wsl --install --no-distribution
```

Перезагрузите Windows, запустите Docker Desktop и дождитесь готовности Linux Engine.
Если установщик требует включить компоненты отдельно:

```powershell
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
```

После этого также нужна перезагрузка. Если проблема остаётся, проверьте доступность
виртуализации в BIOS/UEFI; в виртуальной машине может понадобиться nested virtualization
на стороне хоста. Затем выполните `docker info`, `npm run docker:up` и `npm run test:smoke`.
Автоматическая перезагрузка не выполняется.

## Размещение на VPS с HTTPS

### Индексация временно запрещена

До запуска магазина `public/robots.txt` запрещает обход всех страниц, `index.html`
содержит метатег `robots` с `noindex`, а Nginx и PHP API возвращают
`X-Robots-Tag: noindex, nofollow, noarchive, nosnippet` (включая ответы с ошибками).
Это указания поисковым роботам; доступ по URL остаётся открытым.
После подключения домена эти ограничения сохраняются. Включать индексацию нужно
отдельно: изменить `public/robots.txt`, убрать метатег и заголовки в
`docker/nginx.conf` и `backend/public/index.php`, затем пересобрать приложение.

### Развёртывание

#### Текущее размещение через Hostinger connector

Магазин развёрнут на VPS `1151611` (`srv1151611.hstgr.cloud`, `72.60.25.131`)
как отдельный Docker-проект `nord`. Основной адрес:
<https://nord-light.website>. `www.nord-light.website` постоянно перенаправляет
на основной адрес. Используется существующий Traefik с проверенным публичным
HTTPS-сертификатом. Caddy на этом VPS не запускается.
Параметры размещения без секретов записаны в [.hostinger/site.json](.hostinger/site.json).

Исходники текущего релиза: `/opt/nord/releases/37df780defeb5d7c`.
Compose: `/docker/nord/docker-compose.yml`. MySQL хранит данные в постоянном
томе `nord_mysql_data`; порт базы не опубликован. В базе находятся
15 категорий и 108 товаров (включая 100 тестовых ламп), пользователей и заказов нет.
Перенос данных из других размещений не выполнялся.

SMTP настроен через Resend для `notify.nord-light.website`; production
`mail-worker` запущен с профилем `smtp`. Тестовое письмо на адрес проверки
Resend принято сервисом. Подтверждение регистрации и восстановление пароля
проверены на отдельной тестовой базе с Mailpit; отправку реальному получателю
после включения Resend ещё нужно проверить вручную. Ключ Resend хранится
локально в `.env.docker` и отдельно в `/docker/nord/.env` на VPS; не заменяйте
серверный файл локальным целиком.
Онлайн-оплата в существующем приложении не реализована.
Чат на VPS использует `gpt-6-luna` и отвечает через серверный `OPENAI_API_KEY`.

`node scripts/hostinger-compose.mjs` создаёт архив только из разрешённого списка
исходников и компактные Compose-файлы в `.hostinger/generated/`.
Пароли и ключи сохраняются отдельно в игнорируемых `.env.hostinger.production`
и `.env.hostinger.verify`; существующие секреты скрипт сохраняет.
SSH-ключ размещения: `.secrets/hostinger-nord`; он добавлен на VPS с разрешения
владельца. Не публикуйте эти файлы.

Порядок нового релиза: загрузить архив в отдельный каталог релиза, собрать
образы из `backend/Dockerfile` и `Dockerfile`, затем обновить Compose в
`/docker/nord/docker-compose.yml` через SSH и запустить его с существующим
`/docker/nord/.env`. `pull_policy: never` позволяет использовать подготовленные
образы без Docker Registry. Перед обновлением существующей базы сохраните
резервную копию; не заменяйте серверный `.env` локальным файлом целиком.

В Namecheap настроены A-запись `@` → `72.60.25.131` и CNAME `www` →
`nord-light.website`. На сервере `SITE_DOMAIN=nord-light.website` в
`/docker/nord/.env`; `APP_URL` и `FRONTEND_URL` берутся из него. При смене
домена сохраните остальные переменные и том MySQL, обновите DNS и Compose,
после чего проверьте HTTPS, API, чат и перенаправление `www`.
Запрет индексации действует и на новом домене.

#### Общий вариант VPS с Caddy

1. Установите Docker Engine и Compose по инструкции для вашей ОС.
2. Скопируйте репозиторий на VPS. Не переносите старые `.env.local` и `backend/.env`.
3. Создайте `.env.docker`: через `npm run docker:setup`, если установлен Node.js,
   либо скопируйте `.env.docker.example`, заполните оба пароля случайными значениями
   (`openssl rand -hex 32` для каждого), а `APP_KEY` и `BACKUP_ENCRYPTION_KEY` —
   независимыми ключами (`openssl rand -base64 32` для каждого). На Linux: `chmod 600 .env.docker`.
4. Укажите `SITE_DOMAIN=shop.your-domain.com`, свой `ACME_EMAIL` и
   `FRONTEND_URL=https://shop.your-domain.com`. Оставьте `HTTP_BIND=127.0.0.1`.
5. Настройте `SMTP_HOST`, `SMTP_PORT` (обычно 587), `SMTP_ENCRYPTION=tls`,
   `SMTP_USERNAME`, `SMTP_PASSWORD` и `MAIL_FROM` вашего почтового провайдера.
   Production запрещает отправку SMTP без TLS. Настройте SPF/DKIM/DMARC у провайдера.
6. Настройте DNS, откройте 80/443 в firewall и запустите:

```bash
docker compose --env-file .env.docker -f compose.yaml -f compose.vps.yaml up -d --build --wait --wait-timeout 180
docker compose --env-file .env.docker exec backend php bin/create-admin.php admin@your-domain.com
```

Сайт будет доступен на `https://shop.your-domain.com`. MySQL и PHP-FPM остаются без
публичных портов. Не публикуйте порт MySQL для подключения браузера или админки.
Получение публичного TLS-сертификата проверяется уже на VPS с настоящим доменом.

Обновление и остановка на VPS используют **оба** compose-файла:

```bash
git pull
docker compose --env-file .env.docker -f compose.yaml -f compose.vps.yaml build --pull
docker compose --env-file .env.docker -f compose.yaml -f compose.vps.yaml up -d --build --wait --wait-timeout 180
docker compose --env-file .env.docker -f compose.yaml -f compose.vps.yaml logs --tail=100
docker compose --env-file .env.docker -f compose.yaml -f compose.vps.yaml down
```

После создания тома изменение `DB_PASSWORD`, `DB_USER` или `DB_NAME` в файле окружения
не меняет существующую базу. Ротация паролей требует изменения пользователя в MySQL
и соответствующего обновления окружения API.

## Резервное копирование и восстановление

Постоянный том защищает от удаления контейнера, но не заменяет резервные копии.
С установленным Node.js:

```bash
npm run db:backup
```

Создаёт зашифрованный AES-256-GCM дамп `backups/nord-<дата>.sql.enc`.
Открытый SQL не записывается на диск при создании копии. Нужен Node.js 22+ для этой команды.
Каталог исключён из Git. Храните копии также вне VPS, ограничьте доступ и проверяйте восстановление.
Ключ `BACKUP_ENCRYPTION_KEY` храните отдельно от архивов: без него восстановить копию нельзя.
Для проверки и расшифровки (существующий файл назначения не перезаписывается):

```bash
npm run db:decrypt -- backups/nord-<дата>.sql.enc backups/restored.sql
```

Восстановление **заменяет таблицы и данные целевой базы**. Делайте его на отдельном тестовом
экземпляре либо после остановки записи и создания актуальной копии. В Linux shell:

```bash
docker compose --env-file .env.docker exec -T db sh -c 'exec env MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -u root "$MYSQL_DATABASE"' < backups/restored.sql
```

Не используйте этот синтаксис перенаправления `<` в PowerShell.
Открытый `restored.sql` содержит персональные данные: удалите его после восстановления.

## Пароли, вход и восстановление

- Новые пароли хешируются Argon2id (19 MiB, 2 прохода, 1 поток), длина 8–128 символов.
  Старые bcrypt-хеши обновляются при успешном входе. Пароли и почтовые токены не возвращаются в API.
- Регистрация требует подтверждения email. Форма повторной отправки: `/resend-verification`.
- После **трёх последовательных неверных паролей** аккаунт блокируется в базе без таймера;
  старые сессии отзываются, письмо сброса ставится в очередь. Правильный пароль до третьей ошибки
  обнуляет счётчик. После блокировки правильный пароль уже не помогает — нужен сброс через почту.
- Ручной запрос сброса: `/forgot-password`. Одноразовая ссылка действует 20 минут;
  новый пароль должен отличаться от прежнего. Сброс снимает блокировку и отзывает все сессии.
- Администратор дополнительно подтверждает вход одноразовой ссылкой из письма (10 минут).
  Это подтверждение владения почтой, а не независимый аппаратный фактор или TOTP.
- Ссылки содержат токен во фрагменте `#token=...`; он не попадает в HTTP URL и access-логи.
  Приложение убирает фрагмент из адреса и требует явного подтверждения действием пользователя.
  В базе хранятся только SHA-256-хеши токенов. Почтовая очередь зашифрована ключом `APP_KEY`.
- Сессия хранится в `HttpOnly`, `SameSite=Lax` cookie с областью `/api`; в production также `Secure`.
  Максимум 12 часов для покупателя, 30 минут для администратора; простой 30 минут завершает сессию.
  Старый bearer-токен удаляется из `localStorage`. Для изменений требуются CSRF-токен и допустимый Origin.
- Ограничены запросы входа, регистрации, восстановления, заказов и записи в API.
  За Caddy реальный IP принимается только от доверенного контейнера; произвольный X-Forwarded-For игнорируется.

Политика жёсткой блокировки означает, что знающий чужой email может попытаться заблокировать
аккаунт тремя ошибками. Ограничение запросов снижает риск, но не устраняет это свойство выбранного правила.
Доступ к почте должен оставаться доступным владельцу аккаунта.

При обновлении существующей базы миграция отзывает старые сессии и требует подтверждения
email существующих пользователей. Сначала сделайте резервную копию; не удаляйте том.
Для свежего запуска схема применяется из `schema.sql`, затем сервис `migrate` добавляет защиту.

Если SMTP временно недоступен, запрос восстановления всё равно получает общий ответ,
а worker повторяет отправку до 6 раз. Следите за `docker compose --env-file .env.docker logs mail-worker`.
После исправления SMTP повторить неуспешные задания:

```bash
docker compose --env-file .env.docker exec backend php bin/mail-worker.php --retry --once
```

Пользователь также может запросить новую ссылку; истёкшие ссылки не разблокируют аккаунт.
`.env.docker` содержит ключи и служебные пароли открытым текстом: ограничьте доступ на уровне ОС.
Шифрование MySQL-тома на диске требует настройки дискового шифрования VPS и автоматически Docker не включается.

## Если в Supabase остались реальные данные

В репозитории нет доступа к удалённому Supabase и выгрузки его данных. Этот запуск создаёт
новую MySQL-базу; он не переносит автоматически пользователей, товары и заказы из облака.
Перед окончательным отключением Supabase потребуется:

1. Получить схему и экспорт таблиц, сопоставить идентификаторы и связи с MySQL-схемой.
2. Перенести данные отдельным проверенным импортом; PostgreSQL-дамп нельзя напрямую
   загрузить в MySQL. Сверить количество записей, суммы заказов и остатки.
3. Если использовался Supabase Storage — скопировать файлы и заменить URL. Сейчас товары
   используют внешние URL картинок; собственного сервиса загрузки файлов в проекте нет.
4. Продумать перенос входа пользователей: совместимость хешей требует проверки;
   существующие сессии Supabase не переносятся. При необходимости организовать сброс паролей.
5. Остановить запись в старую базу, выполнить финальный импорт, проверить сценарии и только
   затем переключить домен и отключить старый сервис.

Онлайн-оплата существующим API не реализована. Заказ сохраняется в MySQL;
автоматических писем о заказе или списания оплаты пока нет. SMTP используется для безопасности аккаунта.

## Разработка без контейнера фронтенда

### Чат-помощник

Кнопка «Помочь с выбором?» открывает чат на всех страницах магазина. Помощник
использует OpenAI Responses API и читает актуальные товары из локальной MySQL:
цены, остатки, описания, ограничения и совместимость. На странице товара получает
контекст открытой модели. Подбор возвращает ссылки на карточки. Товары `TEST-LAMP`
остаются явно помеченными как вымышленные.

В локальном `.env.docker` задайте серверные переменные:

```dotenv
OPENAI_API_KEY=your-local-api-key
OPENAI_CHAT_MODEL=gpt-6-luna
```

Не добавляйте ключ в `VITE_*`, исходники или Git.

По умолчанию используется GPT-6 Luna для ответов и проверок тематики.
Для неё явно установлен `reasoning.effort: none`, чтобы не расходовать токены
на дополнительные рассуждения, и `temperature: 0` для меньшей вариативности ответов и проверок тематики.

После изменения ключа или кода:

```bash
npm run docker:up
npm run test:chat
```

`test:chat` проверяет поиск и инструменты на локальном каталоге из 100 ламп,
используя подставные ответы провайдера без платных запросов. Сам чат делает
платные API-запросы из PHP, с `store: false`. История живёт в памяти вкладки,
сохраняется при переходах между страницами и очищается кнопкой нового диалога
или перезагрузкой. В базу диалоги не записываются. Сообщения и выбранные публичные
данные товаров передаются OpenAI; персональные данные в чат вводить не следует.

Бот не получает данные аккаунтов и заказов, не выполняет произвольный SQL и не
меняет каталог. Факты о сайте задаются в `chatStoreInfo()` в `backend/src/chat.php`.
Тематика ограничена помощью покупателю NORD. Отдельная проверка перед генерацией
отклоняет посторонние задачи, включая код, лендинги и рекламные тексты, даже если
они упоминают магазин. Перед выдачей ответа выполняется повторная проверка его
тематики; HTML и фрагменты кода дополнительно блокируются сервером. При отказе
возвращается готовый текст о тематике чата без товаров. Некорректный результат
проверки не разрешает выполнение запроса. Правила: `backend/src/chat-policy.php`.
Подбор по помещению, площади, высоте потолков и цвету света, а также связанные
с покупкой приблизительные расчёты яркости, количества ламп и стоимости разрешены.
Для существующего светильника помощник уточняет цоколь и другие недостающие
условия совместимости, вместо обещания достаточной мощности только по площади.
`npm run test:chat:scope` дополнительно проверяет ограничения на реальном локальном
API (код, смена роли, смешанные запросы и обычные консультации). Эта отдельная
интеграционная проверка использует платные вызовы OpenAI и запускается только для localhost.
Неопубликованные сроки доставки, контакты и способы оплаты он должен обозначать
как неизвестные. Онлайн-оплата пока не реализована. Запросы защищены CSRF,
ограничением длины истории и лимитами 15 запросов в минуту / 200 в сутки на IP.
При недоступности провайдера вопрос остаётся в поле ввода для повторной отправки.

Документация: [вызов инструментов OpenAI](https://developers.openai.com/api/docs/guides/function-calling),
[модель GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna).

После запуска контейнеров:

```bash
npm ci
npm run dev
```

`npm run dev` сначала проверяет API. Если он недоступен, запускает локальный Docker-стек
и ожидает готовности API, затем открывает Vite на порте 5173. Если Docker требует
перезагрузки или недоступен, команда завершается с пояснением вместо запуска одного фронтенда.
При уже работающем API (в том числе нативном PHP) Docker повторно не запускается.
Vite проксирует `/api` на порт `HTTP_PORT` из `.env.docker` (по умолчанию `127.0.0.1:8080`).
Для нестандартного адреса Vite задайте соответствующий `DEV_FRONTEND_URL` в `.env.docker`
и пересоздайте локальные контейнеры; проверка Origin не допускает произвольные адреса.
Старое значение `VITE_API_URL` в `.env.local` может переопределить этот адрес:
удалите его или установите `/api`. Docker-сборка локальные env-файлы не копирует.

```bash
npm run build
npm run format:check
```

Миграции существующей базы применяет сервис `migrate` с блокировкой от параллельного запуска.
Скрипты `/docker-entrypoint-initdb.d` выполняются только при создании пустого тома.

### Статус проверок при подготовке

На VPS с PHP 8.5.12 и MySQL 8.4.13 прошли 55 интеграционных проверок API с Mailpit
и 22 проверки защитных функций. Тестовые данные удалены, проект `nord-verify`
остановлен с сохранением журнала и тома. Для публичного production-адреса прошли
67 проверок HTTPS, SPA-маршрутов, API, cookie, CSRF, закрытых env-файлов и noindex.
Сохранность каталога и миграций проверена перезапуском контейнера MySQL.
Проверены сборки Vue/PHP/Nginx, Compose и шифрование/подмена резервных копий.
Визуальная проверка через Chrome заблокирована системной политикой,
запрещающей DevTools remote debugging; клики и внешний вид форм не подтверждены.
